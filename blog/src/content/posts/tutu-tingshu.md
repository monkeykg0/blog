事情的起因很简单：想给孩子听《西游记》广播剧。打开市面上的听书 App，不是开屏广告就是会员弹窗，好不容易点进去了，首页还给你推一堆乱七八糟的短视频内容。我手里正好有台闲着的 VPS，索性花了两天，自己撸了一个——「兔兔听书屋」。

现在它长这样：兔子主题的暖色界面，书架上摆着一排专辑封面，点进去就能听，锁屏能控制，换个设备接着上次的进度播。目前架子上已经有 9 个专辑、1774 集、约 265 小时的内容：西游记、三国演义、水浒传、红楼梦、格林童话、安徒生童话、一千零一夜、诗词启蒙、古词吟唱。

## 整体架构

架构上完全没有追求花活，就是「静态前端 + 小后端 + 文件直出」的经典组合：

```
浏览器 (React PWA)
   ├── /tutu/        静态前端，nginx 直出
   ├── /tutu/files/  音频文件，nginx alias 直出（原码率，不转码）
   └── /api/media/   Go API (8081, systemd)
                        └── MySQL：跨设备进度 + 收听统计
```

- **前端**：Vite + React 18 + TypeScript + zustand + Tailwind，做成 PWA，手机上「添加到主屏幕」之后跟原生 App 没什么区别
- **后端**：一个单 `main.go` 的 Go 服务，跑在 systemd 里，只负责专辑元数据、播放进度和收听统计
- **音频**：不转码、不走后端，nginx 直接 serve 文件。VPS 带宽比 CPU 便宜，转码纯属自找麻烦
- **元数据**：每个专辑一个目录，里面一份 `album.json`（标题、封面、集列表、时长），Go 启动时扫一遍进内存

音频保持原码率是一开始就定下的决策。听书内容大多是 64-128kbps 的人声，再转码省不了几个钱，反而要维护一套转码管道。KISS。

## 给小朋友设计界面

这个站的主要用户是小朋友和家里的老人，所以界面设计只有一个原则：**大**。

- 播放/暂停按钮做得巨大，进度条是一根胡萝卜，滑块是一只兔子，拖起来有明确的视觉反馈
- 整体奶油暖色调，没有任何广告位、推荐位、弹窗——书架上只有家长导入的内容
- 曲目列表当前播放行高亮描边，一眼能看到「听到哪了」

播放体验上，该有的全都有：

- **Media Session API**：锁屏和控制中心显示封面、标题，能上一集/下一集。这个 API 现在 iOS Safari 和 Android Chrome 支持都很好，几十行代码换来「原生级」的体验，性价比极高
- **断点续播**：每集听到哪自动记录，下次打开从那一秒继续
- **自动连播**：一集完了自动下一集，睡前故事场景刚需
- **倍速、定时关闭**：给大人用的，定时关闭配睡前故事同样是刚需

## 没有登录体系，怎么做跨设备同步？

这是整个项目里最值得写的一块。

我不想做注册登录——目标用户是各个家庭的老人小孩，让他们注册账号记密码，等于劝退。但「手机听了一半，平板接着听」的进度同步又必须要有。

第一版偷懒方案：所有人共享一个 token，进度按 token 存。上线一天就翻车了——**所有人的播放历史串在一起**，我听到三国 100 集，孩子那边西游记的进度也被顶掉了。

第二版换成了设备维度的匿名标识：

1. 前端首次访问时生成一个 UUID，存 `localStorage`
2. 之后所有 API 请求都带上 `X-Device-Id` 头
3. 进度表主键改成 `(user_id, album_id)`，每个设备每个专辑一行

中间还考虑过「IP + User-Agent 指纹」方案，很快否决：家庭场景下全家共用一个 Wi-Fi 出口 IP，爷爷的平板和孙子的平板 UA 可能一模一样，根本分不开。localStorage UUID 虽然清缓存会丢，但对「听书进度」这种丢了也不心疼的数据，完全够用。

收听统计也顺手做了：播放中每 30 秒向后端发一次心跳，上报真实收听秒数（暂停不算），落到 MySQL。管理接口用独立的 `ADMIN_TOKEN` 保护，不打进前端包——前端能看到的接口和管理接口权限彻底分开。

## 内容管道：1774 集是怎么导进去的

一开始只有西游记 138 集，手动整理还凑合。后来一口气加了 1600 多集，靠的是一条固定管道：

```
原始音频 → staging 清洗（Python 硬链接改名）→ media-import.sh → rsync 上服务器 → POST /api/media/refresh
```

几个关键点：

**标题清洗**。网上收来的音频文件名惨不忍睹，充斥着「【某某公众号】」「耗时 XX 整理」、主播名后缀之类的垃圾字段。清洗放在 staging 阶段做，用 Python 把文件**硬链接**成干净的名字——不动原始文件，改名成本为零，清洗规则写错了随时重来。

**导入脚本**。`media-import.sh` 负责按自然序给集数编号、用 ffprobe 读时长、生成 `album.json`。上新专辑时前后端代码零改动：跑脚本 → rsync → 调一下 refresh 接口，书架上就多了一个专辑。

**烂文件要提前筛**。一千零一夜 943 集里混着一个损坏的源文件（第 601 夜），ffprobe 读不出时长直接让脚本中断。现在的流程是导入前先全量 ffprobe 过一遍，坏的剔除。

## 踩坑记录

**坑 1：C locale 下的中文 shell 脚本。** 我的部署环境 bash 默认 C locale，脚本里一碰中文文件名就出各种诡异问题。脚本开头必须 `export LC_ALL=en_US.UTF-8`，一劳永逸。

**坑 2：bash 变量后面紧跟全角标点。** `$VAR，` 这种写法，bash 会把全角逗号当成变量名的一部分去解析，值直接变空。凡是变量后面接中文标点，必须写成 `${VAR}，`。这个坑不踩一次很难意识到。

**坑 3：共享 token 存进度。** 上面说过了，多用户场景下任何「共享标识」存个人状态都是定时炸弹，哪怕产品当时只有一个家庭在用。按多用户设计从第一天就该做对。

## 现状与后续

站点上线两天，全链路（导入 → 部署 → 手机锁屏播放 → 换设备续播）验证通过，已经开始给亲戚朋友的家庭用了。后面有用户量了再考虑正式的登录体系，现阶段匿名设备标识足够。

回头看，这个项目没有用任何新潮的东西：React、Go、nginx、MySQL、一个 shell 脚本。但「给自己家人做产品」的感觉真的很好——没有 KPI、没有增长指标，唯一的验收标准是孩子睡前那句「我要听大闹天宫」。
